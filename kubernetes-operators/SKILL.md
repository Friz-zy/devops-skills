# Kubernetes operator engineering

An operator is a distributed **level-triggered reconciler**, not a request handler. Reconciliation must converge from observed state, tolerate retries/duplicates and avoid destructive operations on unrelated resources.

## Workflow

1. Confirm a CRD/operator is justified over Helm/Deployment/Job; inspect target Kubernetes/controller-runtime versions, installed CRDs, version skew, owned and external resource lifecycle, privileges and failure semantics.
2. Define a small typed `spec` contract, structural OpenAPI schema, defaults, validation, status/conditions, ownership, deletion and upgrade compatibility before implementing reconciliation.
3. Implement idempotent reconcile, bounded requeues, conflict-safe updates and finalizers; scope RBAC, watches and namespace permissions.
4. Run unit + envtest + real-cluster tests for happy path, retries, conflicts, deletion, upgrades and operator outages. Never install/upgrade CRDs in production without review and data migration plan.

## API and ownership

- Use consistent plural/group/kind/version; add schema descriptions, required fields, type/range/enum validation, defaults and CEL/webhook rules when declarative schema is insufficient. Avoid untyped free-form blobs except intentionally versioned extension fields.
- Maintain backwards-compatible served/storage versions, conversion strategy and storedVersions migration. Test old CR objects under new operator and webhook availability. Defaulting should be deterministic; don't silently rewrite user `spec` after creation.
- Treat `spec` as user intent; expose `status.conditions` with meaningful `Ready`/`Progressing`/`Degraded` and `observedGeneration` matching the processed `metadata.generation`. Update status separately, avoid status churn, and never leak secrets or volatile timestamps unnecessarily.
- Use OwnerReferences only for valid ownership: a namespaced owner cannot own cluster-scoped objects, and cross-namespace owner refs are invalid. Adopt existing resources only after verifying labels/owner UID; never overwrite unrelated objects.

## Reconciliation, finalizers, safety

- Read current state each cycle, compare desired vs observed and **patch the minimal diff**; handle conflicts with retry/re-read. Don't rely on event ordering, cached reads or a one-time create path. Make operations idempotent across controller restarts and leadership changes.
- Finalizer cleanup must be bounded, retryable and observable; add finalizer before creating external resources. On deletion, avoid waiting forever for already-gone resources, and never remove a finalizer before critical external cleanup finishes unless a documented escape hatch is approved.
- For external cloud resources, use stable idempotency keys, scoped identities, timeouts/backoff and authoritative ownership tags; plan orphan detection, out-of-band changes and partial-failure compensation.
- Use controller-runtime work queue/backoff, rate limiting and context cancellation. Avoid tight reconcile loops, broad polling and unrestricted concurrency; watch owned resources and configure predicates without missing generation-independent signals (e.g. deletion/status changes).
- Limit informer/cache scope and RBAC: avoid cluster-wide watches, wildcard verbs and `secrets` read across all namespaces if possible. Leader election for multiple replicas; define readiness/metrics, backpressure and memory limits.
- CRD schema/deletion changes can destroy customer-owned data. Do not use `ownerReference` or garbage-collection policies without explicit retention design; never assume uninstalling an operator removes its CRDs safely.

## Testing gates

```sh
# Use targets generated by the actual Kubebuilder scaffold; inspect Makefile first.
make manifests generate
make test                # envtest requires kube-apiserver and etcd assets
# Optional authorized isolated cluster: kind create cluster; make deploy
```

- envtest starts API server + etcd **without kubelet/controller-manager/GC**; test garbage collection, scheduling, RBAC enforcement, admission integrations and real lifecycle separately in kind/k3d/test cluster.
- Assert schema invalid CR rejection, defaults, desired child resource shape, no-op second reconcile, resourceVersion conflict, unavailable API, duplicate events, finalizer cleanup, external-delete failure, upgrade/conversion and leader failover.
- Test tenant isolation: unprivileged CR input cannot create cluster-admin roles, mount host paths, fetch other-namespace Secrets or select privileged RuntimeClass; validate actual RBAC and admission, not just generated markers.
- Compare generated CRDs/RBAC manifests into Git; ensure no unrelated permission escalation or schema narrowing. Record compatibility with supported Kubernetes versions.

## Handoff

Provide CRD/API contract, controller changes, RBAC/ownership map, migration/deletion plan, envtest and cluster-test evidence, metrics/alerts and outstanding failure modes.
